# はまこく Map

横浜国立大学構内とその周辺にあるシェアサイクルポート（HELLO CYCLING / ドコモ・バイクシェア）・バス停・走っているバスを、簡略キャンパス図の上に表示するアプリです（旧: 横国レンタサイクルマップ、`cyclemap/`）。

- 本番では `https://team301.jp/hamakokumap/` で配ります。常盤祭までは hamakokuex と同じ Node（`app_v1`）に相乗りしています（ADR-0030）
- 見た目は はまこく Exp. にそろえています（#177、#65 で決めた案A「構内案内図」）。詳しくは下の「画面の作り」
- 地図のピンは番号と「その事業者のアプリでいま借りられる台数」だけを出し、名前は一覧に回します。取れない場合は「−」
- 台数はページを開いている間、1分ごとに自動で取り直します（「今すぐ更新」ボタンで手動でも再取得できます。詳しくは下の「自動更新」）
- 定員（最大駐輪台数）は `update.js` で焼き込んだスナップショットで、一覧の「くわしく」にだけ出します
- エリアは**横浜国立大学**と**横浜駅**の2つで、タブで切り替えます（範囲は #65 で決定）
- 横浜駅は自転車を返す側のエリアなので、ピンには借りられる台数の代わりに「返せる空き」を事業者ごとに出します。はまこく Exp. のルート検索が返却先に使うポートには、番号の丸に輪を付けて区別します
- バス停を押すと横浜駅方面の発車時刻（#53。市営バスは遅れも、#178）、走っているバスを押すと次に止まるバス停と終点の到着見込み（#178）、はまこく Exp. の出発地の建物を押すとその出発地で はまこく Exp. へ（#179）
- `/hamakokumap/?kiosk` で展示モード（#180）

## 動かし方

```bash
cd app_v1
npm start          # → http://localhost:3000/hamakokumap/
```

`index.html` をブラウザで直接（`file://`）開いても、Live Server などで静的に配っても動きます。そのときは台数をサーバではなく ODPT から直接取ります（下の「空き台数のリアルタイム取得」）。ただし**バスの位置（#84）はキーが要るので出ません**。画面はバスの行ごと畳みます。

## サーバ側（`server/router.js`）

ページの配信とマップ用の API をまとめた Express の Router です。`app_v1/app.js` から1行でつないでいます。

```js
app.use('/hamakokumap', helmet({ … }), createHamakokumapRouter({ express, getCachedValue, fetchJson, ttlMs }));
```

- express・キャッシュ（`app_v1/utils/cache.js`）・取得（`app_v1/utils/utils.js` の `fetchJson`）は**自分で import せず、`app_v1` から受け取ります**。このフォルダには `node_modules` が無いのと、あとで別のプロセスに切り出せるようにするためです（ADR-0030 の「相乗りをやめるとき」）
- 配るファイルは `index.html`・`ports.js`・`ports.json`・`*.svg`・`icons/` のアイコン（svg・png・ico・webmanifest）だけです。`update.js` などの作業用スクリプトと `server/` は配りません
- CSP はマップ用に `HAMAKOKUMAP_CSP_DIRECTIVES` で決め、`app.js` で helmet に渡しています。hamakokuex の CSP（GA など）とは別です。キャンパス図を `<object>` で読むため `object-src 'self'` を許しています

| パス | 中身 |
|---|---|
| `GET /hamakokumap/` | ページ（`/hamakokumap` は `/hamakokumap/` にリダイレクト） |
| `GET /hamakokumap/api/status` | 事業者ごとの空き台数。`{ operators: { hellocycling: { lastUpdated, stations: [...] }, docomo: { error } } }` |
| `GET /hamakokumap/api/buses` | 走っているバスの位置（#84）と遅れ（#178）。`{ areas: { "ynu-campus": [...], "yokohama-station": [...] }, fetchedAt }` |
| `GET /hamakokumap/api/timetable?date=YYYY-MM-DD` | バス停ごとの横浜駅方面の発車時刻（#53）。`{ date, stops: { "国大中央": [{ time, operator, route, isMidnight, delay }] }, errors }` |
| `GET /hamakokumap/api/trains?date=YYYY-MM-DD` | 横浜駅から出る電車の次の3本（#186）。`{ date, calendar, operators: [{ id, name, lines: [...] }], errors }` |

`api/status` は ODPT の応答を事業者ごとに60秒キャッシュし（同時に何人開いても ODPT へは1回）、`ports.json` に載っているポートだけに絞って返します。片方の事業者が取れなくても、もう片方は返します。

`api/buses` は **ODPT 本番の `odpt:Bus`** を読みます。台数（`api-public`）と違って**キーが要る**ので、`app.js` から `odptKey` を渡しているときだけ答えます（無ければ 503）。各エリアの `bbox` に入っている車両だけに絞り、1台を次の形にして返します。

```json
{ "id": "odpt.Bus:YokohamaMunicipal.20202.03_3.1814",
  "lat": 35.4665, "lon": 139.6210, "azimuth": 220,
  "route": "202", "terminal": "横浜駅西口", "next": "岡野町",
  "occupancy": "空いている", "reportedAt": "2026-10-11T14:43:19+09:00",
  "delay": 3,
  "stops": [
    { "name": "岡野町", "time": "14:45", "expected": "14:48", "kind": "next" },
    { "name": "浅間下", "time": "14:50", "expected": "14:53", "kind": "via" },
    { "name": "横浜駅西口", "time": "15:01", "expected": "15:04", "kind": "terminal" } ] }
```

- `azimuth` は 0 が北の時計回り。地図ではそのまま矢印の向きにしています
- `route` は `odpt:busroute` の末尾（`odpt.Busroute:YokohamaMunicipal.202` → `202`）
- 行先・次の停留所は `odpt:BusstopPole`（2500 件）を12時間キャッシュして id → 名前で引いています。まとめ引き（`owl:sameAs` の繰り返し指定）は上流がタイムアウトするので使えません
- 車両位置は `odpt:frequency` が 30 秒なので、キャッシュも30秒です
- **遅れ（`delay`、分）と、この先のバス停（`stops`）は #178 で足しました。** 地図に写っているバスだけ、`odpt:busTimetable` の時刻表（`odpt:BusTimetable`）を1台ずつ引き（12時間キャッシュ）、`busProgress()` で求めます
  - 遅れは「直前のバス停を通った時刻（`odpt:fromBusstopPoleTime`）− そのバス停の予定時刻」。通った時刻が無いときは「次のバス停の予定時刻を、いま過ぎている分」で下から見積もります。早く走っているときは 0（定刻）
  - `stops` は 次に止まるバス停（`next`）・その次（`via`）・終点（`terminal`）。`expected` は「予定時刻 ＋ いまの遅れ」です
  - 時刻表が取れなかったバスは `delay: null`、`stops: []`。画面では「この先の時刻は取得できませんでした」と出します
  - 0:00〜3:59 は 24 時台として比べます（`timeToMinutesExtended` と同じ考え）

`api/timetable` は `app_v1/services/mainLogic/busDepartures.js` を呼びます。相鉄バス・市営バス・神奈中の adapter をそのまま使うので、**時刻表のコピーは持ちません**。1事業者が落ちても残りは返し、落ちた事業者は `errors` に入ります。

- **市営バスの便には `delay`（分）が載ります（#178）。** 市営バスの adapter が、走っている位置から求めた遅れです（その便がいま走っているときだけ。走っていなければ `null`）。相鉄バス・神奈中は位置を配信していないので常に `null` で、画面では「遅れの情報なし」と出します
- 遅れが入ったので、キャッシュは 60 秒です（以前は 1 時間）。時刻表そのものは各 adapter が `getStaticCachedValue` で持っているので、取り直しても重くなりません

- バス停は `<object>` で読む SVG の中にあるので、親のページから JS で触れません（#65）。`update.js` が名前と位置を `ports.json` の `busStops` に焼き込み、`index.html` が同じ場所にバス停の印（押せる範囲は 28px 四方）を重ねます。地図の SVG に描かれた紫の■は、下地と一緒に灰色に落ちます
- 同じ停留所の別表記（市営の「横浜新道(新道)」と相鉄の「横浜新道」）は `config/geo/busstopPoles/stopNameMap.js` の `stopNames` の先頭にそろえます。地図（OSM 由来）の名前もそれと同じです
- **駅（三ッ沢上町・和田町・羽沢横浜国大）は入れていません。** 地下鉄・相鉄線の adapter は停留所名で引ける形を返さないので、issue #53 の Step 5 として分けてあります
- 土休日は構内の便がほとんど無いので、「{日付} のダイヤでは、この停留所から横浜駅方面の便はありません」と出ます。「持っていない停留所」と「今日は走らない停留所」はサーバの応答からは言い分けられないため、分かることだけ書いています

### `api/trains` — 駅をタップして発車時刻（#186）

`app_v1/services/mainLogic/trainDepartures.js` を呼びます。横浜駅に乗り入れる8路線について、**路線×方向ごとに次の3本**を返します。絞り込みをサーバでやっているのは、1駅1方向で 110〜330 本あるためです（応答は 6KB ほど）。

バスの欄では、遅れているときに**時刻表の時刻に赤い二重線を引いて**見込みに訂正します（#200）。「見込みです」と文で書いても見落とされるためです。

**画面に出るのは、はじめは方向ごとに1本だけです。** JR は4路線×2方向あり、3本ずつ出すと縦に長すぎるためで、1本目を押すと残りの2本が開きます（`state.openDir`）。サーバが3本返しているのは、開いたときに取り直さずに済ませるためです。

```json
{ "date": "2026-10-18", "calendar": "SaturdayHoliday",
  "operators": [
    { "id": "jr", "name": "JR",
      "lines": [
        { "id": "jr-tokaido", "name": "東海道線",
          "delayAvailable": true, "infoAvailable": true,
          "info": { "text": "平常運転", "normal": true },
          "directions": [
            { "id": "Inbound", "name": "東京・上野方面", "finished": false,
              "departures": [
                { "time": "10:32", "type": "普通", "destination": "籠原",
                  "delay": 0, "position": { "from": "戸塚", "to": "横浜" } } ] } ] } ] } ],
  "errors": [] }
```

- `date` は**平日／土休日の判定にだけ**使います。「次の3本」はいまの時刻で決まります
- `delay` は分（`odpt:delay` は秒で来るので直しています）。`position` は走行中の列車の位置で、`to` が `null` なら「その駅に停車中」。**`odpt:Train` は緯度経度を持たない**ので、バス（#84）のように地図上を動かすことはできません
- 1路線が落ちても残りは返します。落ちた路線は `errors` に入ります

**路線によって取れるものが違います**（2026-10-18 に実際に叩いて確認。定義は `app_v1/config/geo/stations/yokohamaStation.js`）。

| 路線 | API | 時刻表 | 運行情報 | 走行中の列車 | 便と結びつく | 遅れ |
|---|---|---|---|---|---|---|
| JR 東海道線・横須賀線・京浜東北根岸線・湘南新宿ライン | チャレンジ | ○ | ○ | ○ | ○ | ○ |
| 京急本線 | チャレンジ | ○ | **×** | ○ 45本 | **×** | **×** |
| 東急東横線 | チャレンジ | ○（渋谷方面のみ） | ○ | × | × | × |
| 相鉄本線 | チャレンジ | ○（海老名方面のみ） | **×** | × | ○ | × |
| 地下鉄ブルーライン | **本番** | ○ | ○ | ○ | ○ | ○ |
| みなとみらい線 | — | **0 件** | × | × | × | × |

- **京急は走行中の列車は配信されているのに、便ごとの遅れが出せません。** 駅の時刻表の便に `odpt:train`（列車の id）が無く、`odpt:Train` 側にも `odpt:delay` が入っていないためです。画面では「遅れの情報が配信されていないので、時刻表どおりです」と出します
- **みなとみらい線は時刻表が 0 件**なので、路線の一覧にも地図の印にも入れていません
- 東急は横浜が終点、相鉄は横浜が起点なので、**時刻表がある方向が片方だけ**です
- **運行情報の出し方は3つだけ**です（#200）。紫は足していません（ADR-0011 は白い紙に青インク、赤は遅れ・満・選択）
  - 配信が無い路線（京急・相鉄）… 「運行情報：−」（灰の囲み）
  - 平常 … 「運行情報：平常運転」（青の囲み）。事業者で文面が違う（JR「平常運転」／東急「東横線は、平常通り運転しています。」／地下鉄「平常運行」）ので、言い方をそろえます
  - それ以外 … 配信された文面を**そのまま**赤の囲みで出します。**遅れと運転見合わせをこちらで判別しません**（本文は自由文で、事業者ごとに言い回しが違うため）
- **本文は長くなります。** 実例（2026-10-18）: 「東海道線は、高崎線内での踏切安全確認の影響で、下り線の一部列車に遅れがでています。」（46字）
  - 2行にすると欄が間延びするので、**1行のまま駅の電光掲示板のように一方向へ送り続けます**（`flowLongInfo()`）。同じ本文を2つ並べた帯にして、1つ目が左へ抜けるのと入れ替わりに2つ目が入るので切れ目がありません
  - **「運行情報：」の札は動かしません。** 流れるのは本文だけです（札 50px は `flex: none`、本文は `.body` の中で送る）
  - スマホ幅での実測: 箱 313px・札 50px・本文欄 254px に対し本文 485px。送り幅は本文＋すき間 32px を 1 秒 35px で送ります
  - 入りきるもの（「平常運転」など）は動かしません。幅が要るので、**欄を DOM に置いてから測ります**
  - **幅の下限（140px）は流すときだけ**に効かせます。短い文にも掛けると、右寄せの箱の左側に余白ができるためです。下限を付けると箱の幅が変わるので、付けてから測り直しています
  - 狭いときは、運行情報が自分の行に落ちてから流れます
  - 動きを控えめにする設定のときは流さず、折り返して全部出します（2つ目の文は隠します）
- **遅れが取れない便は、便ごとに「（非対応）」**と出します（#200）。足の注釈に書いても見落とされるためで、バス停の欄（相鉄バス・神奈中）も同じ扱いです

**ODPT の癖**（`services/adapters/odptRailway.js` に書いてあります）

- 駅の時刻表の深夜便は **24 時超え表記を使いません**。「00:07」で返り、配列の並びでは当日ダイヤの末尾に来ます。比べるときは 0:00〜3:59 を 24:00〜27:59 として扱います（`timeToMinutesExtended` と同じ）
- **`owl:sameAs` のまとめ引きは10件までです。** 11件以上はカンマでつないでも `400 too many OR condition in owl:sameAs` になります。行先・走行中の位置の駅名はこの単位で引き、一度引いた名前はプロセスの間ずっと使い回します（駅名は変わらないため）
- 行先には他社の駅も出ます（東横線の保谷＝西武、横須賀線の成田空港）。事業者ごとに全駅を引くと16事業者で 1.2MB になるので、**出す便に実際に出てきた駅だけ**引いています

**キーは両方要ります。** JR・京急・東急・相鉄はチャレンジ API（`ODPT_CHL_API_KEY`）、地下鉄だけ本番 API（`ODPT_API_KEY`）です。片方でも欠けたら `app.js` が `getTrainDepartures` を渡さず、この口は 503 になります。**チャレンジの期間が終わったら（#100）地下鉄も含めて機能ごと畳む**と決めました（地下鉄だけ残す分岐を持たない、という判断）。

**出るのは横浜市営バスだけです。** 相鉄バス・神奈中バスは車両位置を配信していません（チャレンジ API の `odpt:Bus` は相鉄バスで 0 件。トークン自体は有効で、同じ API の `odpt:TrainTimetable` は 1000 件返ります）。構内は相鉄バスが主力なので、**構内エリアに市営バスが1台もいない時間帯は珍しくありません**（その場合は「いまこの範囲に市営バスはいません」と出します）。

テストは `app_v1/test/hamakokumap.test.js`（`cd app_v1 && npm test`）。

## 地図データの更新方法

ODPT の本番APIキーが必要です（`app_v1/.env` の `ODPT_API_KEY`）。

```bash
cd hamakokumap
node --env-file=../app_v1/.env update.js
```

やっていること:

1. `areas.json` に出てくる事業者（`source`）の `station_information.json` を ODPT から取得
2. 各エリアの `ports` に書かれた `station_id` で引き、名称・座標・定員を取り出す
3. `overrides.json` に同じキー（`"<source>:<stationId>"`）があればマージ
4. `ports.json` と `ports.js` に書き出す

`overrides.json` は読むだけで書き換えないので、手で入れた情報は何度実行しても消えません。フィードから station_id が消えていた場合はエラーで止まります（廃止された可能性があるので `areas.json` から外してください）。

### ポートを1つ足す

1. `areas.json` の該当エリアの `ports` に `{ "source": "docomo", "stationId": "xxxx" }` を追加
2. `update.js` を実行

bbox の外にあるポートは警告が出て、地図上では見切れます。bbox は変えずにそのポートを外すか、エリアを分けてください。

### 事業者を手で上書きする

`overrides.json` の `ports` にキーを足します。

```jsonc
"docomo:5357": {
  "availableOperators": ["docomo", "hellocycling"],  // 実際に借りられる事業者
  "displayName": "…",                                // 省略時はフィードの名称から接頭辞を除いたもの
  "note": "…",                                       // 一覧表で ※ のツールチップに出る
  "capacity": 2,                                     // 定員をこの値にする（フィードの値が明らかにおかしいとき）
  "unreliableDocks": ["hellocycling"],               // この事業者の空きドックを「不明」と出す
  "unlimitedReturn": true                            // ラックが無く何台でも返せる（下記）
}
```

`capacity` と `unreliableDocks` は、横浜駅西口第2駐車場（`hellocycling:20122`）のために入れました。HELLO CYCLING のフィードが定員・空きとも 1000 前後を返し（実際の台数ではない。Q-17）、そのまま出すと「空き 997台」になるためです。定員はドコモ側の値（2台）を使い、HELLO CYCLING の空きは地図で「?」、表では空きドックの集計から外しています。

`source`（どのフィードから取れたか）と `availableOperators`（実際に使える事業者）は別のフィールドです。構内のポートは実態としてドコモ・HELLO CYCLING の両方で使えるのに、HELLO CYCLING 側のフィードには載っていないため、この仕組みで補っています。

## 空き台数のリアルタイム取得

`index.html` は**まず `api/status`（上の「サーバ側」）を試し、無ければ ODPT から直接読みます**。

- `api/status` が返れば、そちらを使う。サーバが ODPT から取ってキャッシュしたものなので、全国分（HELLO は 8MB 超）を毎回ブラウザに落とさずに済む
- 404 やネットワークエラーなら、`api-public.odpt.org` から直接 fetch する。この口はキー不要で `Access-Control-Allow-Origin: *` が付いているので、静的ページからも読める

**`file://` かどうかでは判定していません。** Live Server や `python -m http.server` で配ったときは `http://` だけどサーバの口は無い、という状態になるためです（#54 で実際に「取得できませんでした」と出ました）。

事業者ごとの失敗（片方のフィードだけ落ちた、など）のときは直読みに切り替えません。サーバ側のキャッシュを素通りして全国分を毎回落としてしまうためです。

```
https://api-public.odpt.org/api/v4/gbfs/hellocycling/station_status.json
https://api-public.odpt.org/api/v4/gbfs/docomo-cycle/station_status.json
```

ポートと空き状況の対応は `ports.json` の `feedIds`（事業者 → その事業者のフィード上の station_id）で引きます。同じ物理ポートが事業者ごとに別IDを持つので、`overrides.json` で対応づけます。

```jsonc
"docomo:5357": {
  "feedIds": { "hellocycling": "25263" }   // ← HELLO 側の station_id
}
```

**「その事業者で使えるか」はフィードに載っているかどうかで判定します。** 共同利用の停止などでポートはフィードから消えたり戻ったりする（構内4ポートは一時期 HELLO CYCLING 側から消えていて、2026-10 に復活した）ので、手で固定せずフィードを見ます。どうしても実態と合わないときだけ `overrides.json` の `availableOperators` で上書きできます。

`feedIds` に書いたIDがフィードで引けないときは `update.js` が警告を出し、その事業者では使えない扱いになります。

### 自動更新

ページを開いている間、**60 秒ごと**に `fetchRealtime()` を呼び直します（`index.html` の `REFRESH_INTERVAL_MS`）。

- 間隔はフィードの `ttl`（60 秒）とサーバのキャッシュ（`REALTIME_CACHE_TTL_MS`、60 秒）に合わせています。これより短くしても数字は新しくなりません
- `setInterval` ではなく、取得が終わるたびに次を `setTimeout` で予約します。取得が遅れても前の取得と重なりません。「今すぐ更新」ボタンで取り直したときは、そこから 60 秒後に予約し直します
- タブが裏に回っている間（`document.hidden`）は取りに行きません。戻ってきたとき、前回から 60 秒以上たっていればすぐ取り直し、そうでなければ残りの時間で予約します
- 取得に失敗したときは古い数字を残さず、その事業者を「−」にして「〇〇の台数を取得できませんでした」と出します（手動更新と同じ）。次の自動更新は止めずに続けます
- 見出しの右の「〇〇:〇〇 現在」は、取得が終わった時刻（ブラウザの時計）です
- バス停の時刻の欄を開いていれば、同じタイミングで時刻表（遅れ）も取り直します

## 返せる空きの出し方（#184）

**「返せる空き」は HELLO CYCLING の値ひとつだけを出します。** 以前は事業者ごとに並べていて「空き 4 / 3」のようになり、意味が伝わりませんでした。

HELLO の `num_docks_available` は**両社あわせた実際の空き**を見ているのに対し、ドコモの値は自社ぶんの計算値です（docs/gbfs-port-data.md）。**足しても並べても意味が無い**ので、HELLO の値だけを使います。はまこく Exp. の `TRUSTED_DOCKS_PROVIDER` と同じ考えです。HELLO がいないポート（ドコモにしか無い）は、残った事業者の値をそのまま使います。

**数字はひとつでも、どちらの事業者でも返せます。** それを**数字の横の小さな印**で示します（`opsMark()`）。

| ポート | 印 |
|---|---|
| 両社で使える | 黄■ 赤■ |
| HELLO CYCLING だけ | 黄■ |
| ドコモだけ | 赤■ |

**数字そのものの見た目は全ポートで同じにします。** 札ごと色を変えると、ドコモにしか無いポートだけが赤く塗られて不自然に目立ちました。印だけにすると、数字は横並びで比べられて、事業者は補足として読めます。

「使うアプリ」を HELLO だけに絞ると、印も黄だけになります。凡例も同じ印で出します。

**返す側のエリア（横浜駅）では、借りられる台数に色を付けません。** 主役は「返せる空き」なので、台数は文字だけです。「返す」の下に数字が並ぶだけだと何の数か分からないので、**「借りる」と添えます**。借りる側のエリア（国大）はこれまでどおり、台数に事業者の色を付けます（あちらは台数が先頭に来るので添え書きは要りません）。

## 利用時間外の貸出停止（#201）

GBFS の `station_status` には2つのフラグがあり、**見方が違います**。

| フラグ | 使い方 |
|---|---|
| `is_returning` | **全事業者が `false` のときだけ**「返す: いまは不可」。返す場所（ドック）は事業者で共通なので、1社だけ止まっても返せる |
| `is_renting` | **その事業者だけ**「不可」。自転車は事業者ごとに分かれているので、片方だけ止まることがある |

貸出が止まっているときは、台数の代わりに**「不可」**を赤で出します（地図の札と一覧の両方）。借りられないのに台数が出ていると、行ってから気づくことになるためです。

**実際に `is_renting: false` になる場面は、まだ観測できていません。** 2026-10-18 の昼・夕方に見たかぎり、対象25ポート（HELLO 10・ドコモ 15）とも両フラグが `true` のままでした。構内ポートに時間制限が無い可能性もあります。分岐は `is_returning` と同じ形にそろえてあるので、立てば効きます。

手元で見え方を確かめるときは、ブラウザの開発者ツールで応答を差し替えてください。

```js
// 台数の応答を横取りして、最初のポートだけ貸出停止にする
const orig = window.fetch;
window.fetch = async (...args) => {
  const res = await orig(...args);
  if (!String(args[0]).includes("api/status")) return res;
  const body = await res.clone().json();
  body.operators.hellocycling.stations[0].is_renting = false;
  return new Response(JSON.stringify(body), { headers: { "Content-Type": "application/json" } });
};
// このあと「今すぐ更新」を押す
```

## 空きが負で返ってくることがある（#206）

HELLO CYCLING の `num_docks_available` は **負の値を返すことがあります**。観測例（2026-10-18）:

```json
{"station_id":"9788","num_bikes_available":6,"num_docks_available":-1}
```

横浜銀行横浜駅前支店（HELLO 9788／ドコモ 4516 の共用、定員は HELLO 12・ドコモ 6）。HELLO の空きは「両社あわせた実際の空き」なので、**止まっている台数がラック数を超えると負になる**とみられます。

返せないことに変わりはないので、`returnInfo()` で `Math.max(0, n)` に倒し、**`満`** として出します。台数（`num_bikes_available`）側も同じ扱いにしてあります。

## 「空き 0」は満とは限らない（`unlimitedReturn`）

**ドコモのポートには、ラックが無く何台でも返せる型があります。** そのポートの `num_docks_available` は固定値で意味を持たず、**`空き 0` を「満」と読むと、実際には返せるポートを「返せない」と出してしまいます**（詳しくは docs/gbfs-port-data.md）。

**どちらの型かはフィードから見分けられません。** 各社のアプリでそのポートを開いて確かめるしかないので、確かめた結果を `overrides.json` の `unlimitedReturn: true` に書きます。横浜駅では次の4件が該当します（2026-10-12 にアプリで確認）。

| ポート | フィードの値 |
|---|---|
| 横浜スカイビル前（`docomo:2064`） | 定員 0 / 台数 0 / 空き 0 |
| 横浜スカイビル前-2（`docomo:2098`） | 定員 0 / 台数 0 / 空き 0 |
| アソビル（`docomo:2103`） | 定員 4 / 台数 0 / 空き 0 |
| 横浜みなと第一生命ビル（`docomo:623`） | 定員 2 / **台数 5**（定員より多い） / 空き 0 |
| 横浜ベイクォーター（`docomo:2004`） | 定員 23 / 台数 0 / 空き 22（**つじつまが合うのに無制限**） |

**フィードの数字から型を当てることはできません。** 横浜ベイクォーターは「台数 ＋ 空き ＝ 定員」がきれいに成り立つのに、アプリでは何台でも返せます。つまり「つじつまが合わない」は手がかりになっても、「つじつまが合う」は根拠になりません。判定ロジックは書かず、**アプリで確かめた事実だけを書きます**。

横浜三井ビルディングと横濱ゲートタワーは未確認です。つじつまは合っていますが上のとおり根拠にならないので、本当は無制限かもしれません。いまは数字を出しています。確かめたら足してください。

`unlimitedReturn` のポートは、地図でも一覧でも数字を出さず「空きあり」と出します。ただし `is_returning` が `false` のときは「いまは不可」に変わります。

## 共用ポートの数字の読み方

構内4ポートは HELLO CYCLING とドコモ・バイクシェアで同じラックを共用していますが、**2つのフィードが返す値は一致しません**（2026-10-04 に確認）。

| | 自転車の台数 | 空きドック | 定員 |
|---|---|---|---|
| 意味 | その事業者のアプリで借りられる台数 | ラックの空き（共用） | ラックの総数 |
| フィード間 | **違う**（各社の自社分） | **同じ** | **違う** |

4ポートとも「HELLO CYCLING の台数 ＋ ドコモの台数 ＋ 空きドック ＝ 大きい方の定員」が成り立ちます。そこで

- **台数**は事業者ごとに出す（自分が使うアプリの分しか借りられないため）
- **空きドック**は共用なので1列にまとめる（割れていたら両方出す）
- **定員**は大きい方をラックの総数として採用し、事業者ごとの申告値は `capacityByOperator` に残してツールチップで見せる

としています。

## 地図（SVG）の更新方法

建物・道路・敷地・門・バス停は OpenStreetMap（Overpass API）から取ってきて SVG にしています。APIキーは要りません。

```bash
cd hamakokumap
node drawArea.js ynu-campus                  # Overpass から取得して campus-ynu.svg を生成
node drawArea.js ynu-campus --cached         # 前回の取得結果（osm-cache/）から再生成
node drawArea.js ynu-campus --kiosk          # 展示モード用の横長の地図（campus-ynu-kiosk.svg）
node drawArea.js yokohama-station            # 横浜駅（yokohama-station.svg）
node drawArea.js yokohama-station --kiosk    # 横浜駅の展示モード用
```

**地図は1エリアにつき2枚あります**（通常用と展示モード用）。`--kiosk` は `areas.json` の `kiosk` の範囲で描き、取得結果は `osm-cache/<id>-kiosk.json` に別に置きます。詳しくは下の「展示モード用の横長の地図」。

Overpass は混雑していると 504 を返すことがあります（2026-10-11 には 5 回続けて 504 が返り、数分おいて通りました）。その場合は時間をおいて再実行してください。

**SVG を作り直したら、続けて `update.js` も実行してください。** バス停の位置（`busStops`）・はまこく Exp. の出発地の建物の形（`departures`）・地図に描いた文字の範囲（`labelObstacles`）を `ports.json` に焼き込んでいて、作り直さないと古い位置のままになります。ずれているとテスト（`app_v1/test/hamakokumap.test.js`）が落ちます。

ポートを取り直す必要がない（SVG や `areas.json` の `departures` だけ直した）ときは、キーの要らない `node update.js --svg-only` で足ります。ポートの位置・定員と `updatedAt` は前回のまま、SVG から拾う値だけを書き直します。

SVG は生成物なので手で直さず、`areas.json` の `osm` で調整します:

- `buildingLabels`: OSM 上の建物名 → 表示名。ここに書いた建物だけラベルが出ます（全部出すと潰れるので、目印になるものだけ）。`name` が無く `name:ja` だけの建物（横浜駅の駅舎など）も、`name:ja` の値で指定できます。ただし**出発地の建物（`departures`）はここに書いてあっても地図には焼き込みません**。名前は重ねる側が出すので、両方に出すと二重になります（下の「名前を出すのは地図か、重ねる側か」）
- `placeLabels`: 載せたい `place` ノードの名前
- `focus`: 強調する敷地の条件（タグの組み合わせの配列）。省略時は `[{ "amenity": "university" }]`。この敷地は色を付け、その内側の建物を濃く、外側の建物を薄く描きます。大学の敷地が無い横浜駅は、駅舎（`building=train_station` かつ `public_transport=station`）にしています
- `showBusStops`: 地図に出すバス停の許可リスト（#184）。書いてあればこれ以外は描きません。横浜駅は停留所が多いのに、大学方面の便があるのは**横浜駅西口だけ**で、ほかは押しても「便はありません」にしかならないので絞っています
- `hideBusStops`: 地図に描かないバス停の名前（#177）。国大は「西釜台」「釜台住宅第2」（#65 で決定）。釜台住宅第2 はいまの範囲の外ですが、北へ広げたとき（#181）にも出さないので先に書いてあります。`campus-ynu.svg` はこの設定で描き直してあります
- `minBuildingArea`: 強調する敷地の外にある建物のうち、この面積（m²）未満のものを描きません。省略時は 0（全部描く）。横浜駅は 300 にしています。建物が密集していて、全部描くと目印が埋もれるためです（`buildingLabels` に書いた建物は小さくても描きます）

門（`barrier=gate` で名前つき）、バス停、地上の線路（`railway=rail`。トンネルと地下は除く）は自動で載ります。ただし**バス停は見えません**（下の「名前を出すのは地図か、重ねる側か」）。

### 道の描き分けと、水面の見分け（#184）

人に見せたときに「構内のメインストリートが点線で見づらい」「大きな道路と川の見分けがつかない」と言われたので直しました。

**`highway=pedestrian` は小道ではなく「車を入れない通り」です。** 構内のメインストリートがこれで、`road-foot`（2px の点線）に落としていたので通りに見えていませんでした。`road-walk` という層を足して、縁取り付きの実線で描きます。`footway` / `path` / `steps` / `cycleway` は点線のままです。

表の上から順に描く（＝下にある太い道ほど上に乗る）ので、歩道の点線がメインストリートを分断することもありません。

**道は細いものから順に描きます**（`roadOrder`）。あとに描いたものが上に乗るので、**大きい道が上**になります。逆だと大きい道の上に路地や歩道が乗って、交差点が汚れて見えます。構内のメインストリート（`road-walk`）はサービス道より上・一般道より下に置いています。構内では主役ですが、外の大きい道に勝つほどではないためです。

| OSM の `highway` | 層 | 描き方 |
|---|---|---|
| `trunk` / `primary`（＋ `_link`） | `road-major` | 18px、黄土色 |
| `motorway` / `motorway_link` | **描かない** | 歩けないので載せない |
| `secondary` / `tertiary` / `unclassified` / `residential` | `road-street` | 8px、白 |
| `service` / `living_street` | `road-service` | 5px、白 |
| **`pedestrian`** | **`road-walk`** | **6.5px、うっすら色を付けた実線** |
| `footway` / `path` / `steps` / `cycleway` | `road-foot` | 2px、点線 |

**水面と大きな道路は色味で分けます。** どちらも淡い色だったので、とくに夜の紙では見分けがつきませんでした（`--water: #2f4656` と `--road-major: #4a4a46`）。水面をはっきりした青にして縁（`--water-edge`）を付け、大きな道路は黄土色へ寄せています。**色相で 60 度以上離れていること**をテスト（`app_v1/test/hamakokumap.test.js`）で見ているので、palette を触るときは両方を見てください。

**ただし、SVG の色だけ直しても効きません。** `index.html` が下地の地図に CSS の `filter` を掛けていて、以前は彩度を完全に落としていました。それだと川も大きな道路も同じ灰色になります。いまは `--base-filter`（`saturate(0.72)` など）で**色味を残したまま**地図を後ろに下げ、不透明度（`--base-opacity`）で静かにしています。ここを彩度ゼロに戻すと、この章の工夫はすべて無駄になります。

**走っているバスは灰色です。** 横浜駅のまわりは台数が多く、青のままだと主役のシェアサイクルのポートと競ります（`index.html` の `--bus-muted`）。選んでいるバスだけ赤になります。

**大きな水面は `relation`（multipolygon）で描かれています。** Overpass のクエリが `way` しか取っていなかったので、**帷子川の河口（横浜ベイクォーターの前の水面）がまるごと抜けていました**。横浜駅の地図の東側に大きな空白があったのはこれです。いまは `relation["natural"="water"]` も取り、member の way をつないで輪にし（`stitchRings()`）、`<path fill-rule="evenodd">` で描いています。外側・内側（role）は見ていません。evenodd なので、外側の輪の中に入った輪は自動的に穴になります。

> `buildQuery()` が返す文字列はそのまま Overpass に送られます。**中に JS のコメントを書くと 400 になります**（一度やりました）。

**自動車専用道路（`motorway` / `motorway_link`）は描きません。** 歩けないので「構内から横浜駅まで」の案内図には要らず、とくに横浜駅では首都高が地図をほぼ覆ってしまい、その下の新田間川が見えませんでした。地上の道である `trunk`（横浜新道・国道1号）と `primary`（環状1号・県道80号）は、バス停も載るので描きます。構内の第三京浜もこの判断で消えます。

### 名前を出すのは地図か、重ねる側か

地図（SVG）と、その上に重ねる層（`index.html`）の両方が名前を出すと、**同じ名前が二重に出ます**。しかも地図の文字は拡大に合わせて大きくなるのに重ねる側は px 固定なので、寄るほど離れていきます（展示モードでとくに目立ちました）。そこで、どちらが出すかを1つに決めてあります。

| 地図に出るもの | 名前を出すのは | 地図（SVG）側 |
|---|---|---|
| シェアサイクルポート | 重ねる側 | もともと描かない（ピンは全部重ねる側） |
| 出発地の建物（`departures`） | 重ねる側（`dep-label`） | 形（`<polygon data-name>`）だけ描き、**名前は焼き込まない** |
| バス停 | 重ねる側（`.stop`） | ■と名前を**書くが `display: none` で隠す** |
| 走っているバス | 重ねる側 | もともと描かない |
| そのほかの建物（大学会館・学生センターなど） | 地図 | `buildingLabels` のとおり描く |
| 門 | 地図 | 描く |

バス停だけ「書くけれど隠す」なのは、**`update.js` がバス停の位置と名前をこの markup から拾っている**ためです（`busStopMarks()`）。消してしまうと `ports.json` の `busStops` が空になり、重ねる側のピンごと出なくなります。

## 座標系の決め方

SVG の座標系は緯度経度の線形写像です。エリアの `bbox` を決めたら、`update.js` が 1m = 1px の `viewBox` サイズを計算して `ports.json` に書きます（実行時にコンソールにも出ます）。

```
x = (lon - bbox.lonMin) / (bbox.lonMax - bbox.lonMin) * width
y = (bbox.latMax - lat) / (bbox.latMax - bbox.latMin) * height   // 北が上
width  = (lonMax - lonMin) * 111320 * cos(緯度の中央値)
height = (latMax - latMin) * 111320
```

経度は緯度で圧縮されるので cos 補正が入ります。これを無視すると図が横に伸びます。

`drawArea.js` も同じ式で OSM の座標を落とすので、ピンと地図がずれません。bbox を変えたら `drawArea.js` を再実行してください。

ピンは `index.html` が SVG の上に別レイヤで重ねて描くので、SVG 自体にはポートを描きません。

### 地図の印は大きさを変えない

以前（#174）はピンも名前も地図と一緒に拡大縮小していたので、スマホの全体表示では文字が 5px ほどになっていました。いまは

- 下地の SVG と出発地の建物だけを `.map-canvas` に入れて `transform` で拡大縮小する
- ピン・バス停・バスは `.map-markers`（拡大縮小しない層）に置き、**位置だけ**を地図に合わせて動かす（`positionMarkers()`）

という分け方です。台数の札の置き場所（右 → 左 → 右下 → 左下 → 右上 → 左上）は**画面の px で**ほかのピン・札・枠の端と重ならないように選び（`layoutPins()`）、倍率が変わったときだけ選び直します。真横から外したときは、番号の丸から短い線を引きます。

このため `ports.json` の `labelObstacles`（地図の文字の範囲）は、**いまの画面では使っていません**。焼き込みとテストは残してあります。

### 地図を触れるようにする（#174 から引き継ぎ）

地図は **枠（`.map-viewport`）に収めて、中身（`.map-canvas`）を CSS の `transform` で動かします**。ライブラリは入れていません。

- 初期倍率は「全体が枠に収まる倍率」（`fit`）で、**そこより引けません**。上限は `fit` の 8 倍（`MAX_ZOOM_FACTOR`）
- 枠は画面幅に収まるので、**狭い画面でも横スクロールになりません**。枠の高さは絵の縦横比そのまま
- 1本指のドラッグで移動、2本指でピンチ。トラックパッドのピンチ（ctrl 付きのホイール）も拾います。**素のホイールはページのスクロールに残します**
- `＋` / `−` / `全体` のボタンは**地図の外（下）**に置きました。地図の中に重ねると、端のポートを隠すためです（展示モードだけ地図の左下に重ねる）

**ポインタを掴む（`setPointerCapture`）のは、実際に動かし始めてからです。** `pointerdown` の時点で掴むと、あとから出る `click` まで枠に付け替わってしまい、**中のバス停やバスが押せなくなります**。押した場所から 5px（`DRAG_SLOP`）離れるまではタップのつもりとみなし、動かしたあとのクリックは捕捉フェーズで握りつぶします。

### 押したときの欄

バス停・バス・出発地の建物のどれか1つを選べます（同じものをもう一度押すか、×、Esc で閉じる）。

- **バス停** → 横浜駅方面の発車時刻（#53）。「これから」6本と「当日の全便」を切り替え。市営バスの便は遅れ（`N分遅れ` は赤、分かっていて遅れが無ければ「定刻」）、相鉄バス・神奈中は「遅れの情報なし」。「あと N 分」は遅れを足した見込みで数えます
- **バス**（#178）→ 系統・行先・遅れ・混み具合と、次に止まるバス停・その次・終点の到着見込み
- **出発地の建物**（#179）→ 地図の上に吹き出しで「{建物}から帰る」と「横浜駅までの最速ルート →」。リンク先は `/hamakokuex/?from=Library` などで、はまこく Exp. はその出発地を選んだ状態で開きます（`app_v1/config/departures.js`）

バスの位置はキーが要るので静的配信では出ません。そのときは `hideBuses()` が**「地図に出す」のバスと凡例ごと畳みます**。`file://` で開いたときは、取得エラーにせず最初から畳みます。

### 駅の印（#186）

横浜駅の地図に、**事業者ごとに5つ**（JR・京急・東急・相鉄・地下鉄）の札を置きます。1つの駅に6事業者が乗り入れるので路線ごとだと札が多すぎ、かといって駅1つにまとめると「どの路線の時刻か」が押す前に分かりません。

- 座標のもとは `odpt:Station` の `geo:lat` / `geo:long`。**どちらの API も全事業者ぶんは持っていない**ので、JR・京急・東急はチャレンジ API、地下鉄は本番 API から取った値を `app_v1/config/geo/stations/yokohamaStation.js` に書いてあります。`update.js` がそこから `ports.json` の `stations` に焼きます（areas.json 側は `railStations: true` の1行だけ。二重管理を避けるため）
- **相鉄と京急だけは手で置き直してあります。** この印は測量の点ではなく「どこを押せばその路線か」の目印なので、乗り場に寄せたほうが分かりやすいためです。相鉄は odpt の値（JR の 10m 南）だと札が重なって読めないので**新相鉄ビルの上**へ、京急は odpt の値がホームの南端で駅の南に外れて見えるので**45m ほど北**へ寄せました。理由は設定ファイルのコメントに残してあります
- バス停（`busStops`）と違い **SVG からは拾いません**。緯度経度のまま焼いて画面側で投影するので、展示用の横長の地図でもずれません
- **札は重なります。** JR・相鉄・京急・東急は 130m ほどの中に集まっていて、スマホ幅（縮尺 0.43 倍）では JR と相鉄が 10px しか離れません。`layoutStations()` が、重なる札をひと塊とみなして塊の重心を中心に 19px 間隔へ置き直し、ずらした分だけ細い線を引きます。拡大すればずれは 0 に戻ります
  - 塊を作るときは「縦の順に隣と比べる」だけでは足りません。地下鉄は 240m 西にあって縦の順では JR と相鉄の間に入るので、**近い相手が1つでもあれば同じ塊**という作り方にしてあります
- 欄は路線 → 方向 → 便の3段で、**方向ごとに次の1本だけ**出します（押すと残り2本）。方向の名前（「東京・上野方面」など）は `odpt:RailDirection` の `dc:title` が「上り」「下り」しか返さないので、**行先の多い順を見て決めた固定の文字列**です（根拠は設定ファイルのコメント）
- キーが無い配信（`file://`・静的配信・チャレンジ期間後）では、**印・切り替え・凡例ごと畳みます**（バス #84 と同じ扱い）

### 報告・お問い合わせ（#204）

ページの中から team301 に報告できます。**はまこく Exp.（#122）と同じ受け口**（`app.js` の `handleReport`）を呼ぶので、連投の制限（10分に3件）と1日の上限（100件）は**両アプリで共通の数え方**になります。

| 口 | 中身 |
|---|---|
| `GET /hamakokumap/api/report-kinds` | 報告の種類。止めているときは空の配列 |
| `POST /hamakokumap/api/report` | 報告の送信。止めているときは口ごと無い（404） |

- **入口は3か所**: ページの下の断り書きの「こちら」／「くわしく」の断り書きの「こちら」／欄の足（バス停・駅・バス・ポート一覧）

- **展示モードでは出しません**（来場者に触らせない）
- **罠の欄**（honeypot）の名前は `config/report.js` の `REPORT_HONEYPOT` と合わせること。ずれると機械の送信を見分けられなくなるので、テストで照合しています

**報告の種類はアプリごとに出し分けます**（`reportKindsFor("map" | "exp")`）。受け口はどちらの種類も受け付けます。

| 種類 | Exp. | マップ |
|---|---|---|
| 乗り換えに間に合わなかった／ルートが出ない・少ない | ○ | − |
| 便や時刻が実際と違った／遅れの情報がおかしい／その他 | ○ | ○ |
| 台数が実際と違った／ポートの場所や情報が違う／地図の表示がおかしい | − | ○ |

**動作確認は本番の Google フォームに届きます。** `app_v1/.env` の `REPORT_FORM_ACTION` が設定済みなので、手元で起動しても回答シートに入ります。テストと分かる本文にしてください。なお `config/report.js` だけを import して `reportFormConfig()` を見ると「未設定」に見えます（`.env` を読むのは `config/env.js`）。

### 取得できないときの出し方（#203）

「そもそも配信が無い」と「今回取れなかった」が同じ言葉になっていたので、言い分けるようにしました。**色は使わず灰色でそろえます**（ADR-0011 で赤は「遅れ・満・選んでいるもの」に使っており、失敗にも使うと意味が藪むため）。

| 種類 | 言葉 | 例 |
|---|---|---|
| 配信が無い | **非対応** | 「運行情報：非対応」（京急・相鉄）／便ごとの「（非対応）」（遅れ） |
| 取れなかった | **◯◯を取得できませんでした** | 「発車時刻を取得できませんでした」「HELLO CYCLING の台数を取得できませんでした」 |
| まだ返っていない | **◯◯を取得中…** | 「時刻表を取得中…」「台数を取得中…」 |
| この配信では出せない | **この配信では出せません** | `file://` や静的配信で、サーバの口が無いとき |
| データはあるが空 | その状態をそのまま | 「便はありません」「本日の運行は終了しました」 |

**ポートの `−` は分けていません。** 取得中・取得できなかった・その事業者のデータに無い の3つを兼ねます。記号を増やすと読む側が覚えられないので、「くわしく」の凡例に「台数を取得できていない（取得中・取得できなかった・その事業者のデータに無い）」と書いてあります。

なお `ports.js がありません` だけは赤のままです。これは利用者向けではなく、**`update.js` を流し忘れた開発者向け**の文言だからです。

### 駅の出口（#192）

横浜駅の地図に、**駅の出口7件**を三角で出します。**名前は押したときだけ**出します（7つ並べると地図が埋まるため、広い画面でも展示モードでも出しっぱなしにはしません）。

- そのうち**「きた東口C」は外しました**。きた東口B と 23m しか離れておらず、全体表示では三角が重なってしまうためです（残り7件）
- **位置は `areas.json` の `exits` にそのまま書いてあります。** 2026-10-18 に Overpass で引いた値の書き写しで、`update.js` が `ports.json` に写すだけです。出口は動かないので取り直しの仕組みは持たせていません。`drawArea.js` の Overpass 問い合わせにも entrance は足していません（SVG を描き直す必要が無いため）
- **三角は動かしません。** 位置そのものが情報だからです。代わりに**駅の札（#186）のほうをどけます**: 相鉄の札とみなみ西口は 3px、京急の札ときた東口B は 8px しか離れておらず、札は不透明なので三角が消えてしまいます。`layoutStations()` の最後に、三角と重なる札を三角の上か下へ逃がしています（三角は位置の **上に立つ** ので、その高さぶんも見ること。ここを忘れて札が三角の頭に掛かった）

- **三角は線路に垂直な向きで駅を指します。** 先端が出口の位置に当たり、そこから駅のほうを向きます。回す軸は三角の先端なので、回しても位置はずれません
  - 向きは `areas.json` の `bearing`（0=北、時計回り）。OSM の線路（`railway=rail`、駅から 250m 以内、長さで重みづけ）が**方位 34.2 度**なので、それに垂直な **124 度（東南東）と 304 度（西北西）**のうち、線路の中心（35.465963, 139.622529）に向くほうを選んであります
  - **OSM に出口の向きのデータはありません。** これはこちらで決めた描き方です。名前の東西（西口・東口）と計算結果は7件とも一致しました
- **色は青の塗り**（`--ink`）。押すと赤になります
- 三角は 10×9px。小さいので、白のふちどり（`drop-shadow`）で下地から浮かせています

取り直すときは Overpass にこの問い合わせを投げ、`entrance=yes` で名前が「口」で終わるものを拾って `areas.json` を書き換えます（`銀行口` は銀行の入口なので外します）。

```
[out:json][timeout:60];
(
  node["railway"="subway_entrance"](35.461779,139.618451,35.469808,139.628131);
  node["entrance"](35.461779,139.618451,35.469808,139.628131);
);
out body;
```

**`User-Agent` を付けないと 406 になります。** 本家 `overpass-api.de` が ETIMEDOUT / ECONNREFUSED で落ちているときは `overpass.kumi.systems` のミラーで取れました。

### 展示モード用の横長の地図（#180・#181）

展示モードは地図を画面いっぱいに出しますが、**地図の縦横比が画面と合わないと左右（または上下）に余白の帯が出ます**。横浜駅の通常の地図はほぼ正方形（878×894m）なので、16:9 の画面に出すと左右が 2 割ずつ空いていました。

そこで、エリアごとに**展示モード用の横長の地図**を別に持ちます。`areas.json` の `kiosk` に `svg` と `bbox` を書くと、`drawArea.js --kiosk` がその範囲で SVG を描き、`update.js` が `ports.json` の `area.kiosk` に焼き込みます。`index.html` は `?kiosk` のときだけ、地図まわり（`svg`・`bbox`・`viewBox` と、そこから焼いた値）を差し替えます。

| | 通常の地図 | 展示モード用 |
|---|---|---|
| 国大 | 1056×841m（1.26） | **1494×841m（16:9）** 左右に各 219m |
| 横浜駅 | 878×894m（0.98） | **1589×894m（16:9）** 左右に各 356m |

- **ポートは差し替えません。** 緯度経度のまま持っていて、描くときに新しい座標系へ写されます
- **出るバス停は通常と同じにそろえます。** 広げると範囲に入るバス停が増えますが（釜台住宅第一・第3・岡沢下など）、そのほとんどは横浜駅方面の時刻表を持たず、押しても「便はありません」になるだけなので、`update.js` が通常の地図と同じ停留所に絞ります
- 横浜駅の展示用は範囲が 1.8 倍になり、駅の外の小さな建物まで描くと目印が埋もれるので、`kiosk.osm.minBuildingArea` を 600 にして間引いています
- 地図が画面の端まで来るので、**SVG が隅に描いているもの（左下のスケールバー・右下の出典）と、画面側のつまみ・出典がぶつかります。** 展示モードでは拡大縮小のつまみを左の中ほど、出典を下の中央に置いて避けています

### 展示モードの凡例（#184）

展示モードは**一覧（`port-list`）を出さない**ので、記号の意味を読む場所が凡例しかありません。以前は凡例ごと隠していましたが、見出しの下に縦に置くようにしました。

- 文言は展示モードだけ短くします（「バス停（押すと発車時刻）」→「バス停（押すと時刻）」など）。札が大きくなって地図を隠すのを避けるため
- **地図は画面いっぱいなので、凡例は必ず何かの上に重なります。** 1920×1080（展示で使う想定）では、どのポートにも重ならない位置に収まります。1280×720 まで落とすと、いちばん西のポートの番号が凡例の端に隠れることがあります

### 展示モードは触らせず、自動で流す（#187）

常盤祭の展示は**来場者に触らせず、流しておくだけ**にした。

**触れない。** 地図の上のもの（ポート・バス停・バス・出発地の建物）は `pointer-events: none`、拡大縮小のつまみも出さない。欄の「×」も出さない。

**自動でめくる。** `kioskStep()` が `KIOSK_STEP_MS`（既定 10 秒、`?kiosk=秒` で変えられる）ごとに、欄が出るものを順に選ぶ。

- 対象は**バス停・走っているバス・出発地の建物**の3種類（`kioskTargets()`）。シェアサイクルのポートは欄を持たないので対象外
- **その日の便が無いバス停は飛ばす。** 常盤祭の土日は構内の便がほとんど無く、飛ばさないと「便はありません」ばかりになる
- **バスは 1 周で最大 5 台（`KIOSK_MAX_BUSES`、#252）。** 走っているバスは多い時間帯に数十台になり、全部めくると1つのエリアに数分居続けるため。同じバスばかり出ないよう、最後にめくってから長く経つもの（まだめくっていないものが先）から選ぶ。バス停・駅・出発地の建物は全件めくる
- **1エリアを一周したら次のエリアへ移る**（国大 → 横浜駅 → 国大 …）
- **エリアを切り替えた直後は、まず地図を一枚そのまま見せる**（何も選ばない）。横浜駅はバス停が1つしかないので、これが無いと一瞬で通り過ぎる
- **1周するたびに時刻表を読み直してから、めくる対象を作る**（#233）。「その日の便があるか」で絞るので、起動時の読み込みに一度失敗すると、以前は全部のバス停が飛ばされたまま立ち直らなかった

**報告の欄（`<dialog id="report-dialog">`）はスクリプトより前に置く**（#233）。#204 でスクリプトの後ろに置いていたため、スクリプトが動く時点で欄が無く、`getElementById("report-send")` が `null` で例外になっていた。**そこから後ろ（展示モードのめくりの開始・駅の発車時刻の読み込み）がすべて動いていなかった。** インラインのスクリプトから触る要素は、必ずスクリプトより前に置く

**倍率と位置は URL で決める。** 触らせないので、設営でプロジェクタに合わせたら URL を固定して流す。当て込みは `applyKioskView()` が `applyArea()` の中から呼ぶ。**隠れている地図は大きさが 0 で全体表示の倍率が出せない**ので、そのエリアが表に出て測り直したあとに掛ける。

| 指定 | 意味 |
|---|---|
| `?kiosk=10` | めくる間隔（秒）。既定 10 |
| `?zoom=1.4` | 全体表示を 1 とした倍率 |
| `?center=35.4717,139.5921` | その地点を画面の中央に置く。どのエリアの地図かは bbox から決める |

**`?kiosk=秒` の意味が変わった。** 以前（#180）は「操作が無ければ最初に戻すまでの秒数（既定 60）」だった。触らせないなら戻す必要が無いので、その仕掛け（`IDLE_MS` / `resetToInitial`）ごと外し、同じパラメータをめくる間隔に充てている。

**バスは前の位置から滑らせる（`glideBuses()`）。** 位置は 30 秒ごとにしか来ないので、そのままだと 30 秒ごとに瞬間移動する。前の位置から新しい位置へ 30 秒かけて動かす。**見えている位置は最大 30 秒ぶん遅れる**が、止まって見えないほうを取った。直線で動かすので、建物の上を突っ切ることはある（道に沿わせるには経路探索が要る）。

そのために `renderBuses()` は**同じ車両の印を作り直さず使い回す**。作り直すと前の位置が分からず滑らせられない。範囲から出た車両だけ消す。**ふだんの画面では滑らせない**（`KIOSK` のときだけ）。

### 展示モードの動き（#189）

来場者は触らないので、**めくったことが目で分かる**ように動きをつけている。すべて `.kiosk` の中だけで、ふだんの画面では動かない。

- **選ばれたものが跳ねる**（`kioskPop()`）。位置は `placeMarker()` が `transform` で決めているので、**跳ねるのは中身（`svg` / `.body` / `span`）だけ**。印そのものに `transform` を掛けると位置の指定と喧嘩する
- **広がる輪**（`.ping`）が同時に出る。遠目でもどれがめくられたか拾える。終わったら自分で消える
  - **建物（出発地）には出さない。** 輪は点を指すためのもので、面で塗ってある建物には合わない
  - **バスには追従させる。** 動いているので、輪も一緒に動かす（`u.pings`）。止まっているバス停はそのまま
- **欄は徐々に出る**（`kiosk-fade`）
- `prefers-reduced-motion: reduce` のときは、どれも動かさない

### バスを経路に沿って動かす（#189）

#187 で入れた補間は2点を直線で結んでいたので、建物の上を突っ切っていた。**GTFS の経路の形に沿って**動かす。

**データの作り方**

`npm run update:gtfs` が、横浜市営バスの GTFS から `shapes.txt` を読み、**系統ごとの経路の形**を `app_v1/apidata/gtfs/yokohamaMunicipalBus/shapes.json` に焼く（`buildShapesJson()`）。`route_id`（系統番号。`odpt:busroute` の末尾と同じ）→ `shape_id` → 点の列、とたどる。同じ系統でも往復や経由違いで複数の線があるので、系統ごとに配列で持つ。

全国分で 1.8MB あるので、**配るときにエリアのまわりだけに切り落とす**（`loadBusShapes()`、`GET /api/busShapes`）。106KB になる。起動時に1回だけ読む。

| | |
|---|---|
| 焼いたもの | 149 系統 / 588 本 / 86,637 点 |
| 配るもの | 47 系統 / 192 本 / 5,071 点 |

**動かし方**

`routeBetween()` が、前の位置と新しい位置をそれぞれ**経路の線にいちばん近いところ**へ寄せ（`nearestOnLine()`）、その間の点の列を返す。`glideBuses()` はその列の上を 30 秒かけて進む。

**経路に沿っている間は、矢印も実際に進んでいる向きに合わせる**（`headingOnPath()`）。`odpt:azimuth` は位置を取った時点の向きなので、曲がっている途中だと動きとずれる。地図は 1px = 1m の正射なので、画面の向きがそのまま方位になる（北が 0、時計回り。SVG は y が下向き＝南なので `atan2(dx, -dy)`）。

**直線に落ちたときは `odpt:azimuth` のまま**にする（`path.snapped`）。2 点を結んだだけの線は、実際に進んだ向きとは限らないため。

**次のときは諦めて直線にする。** 無理に経路へ寄せると、かえっておかしな動きになるため。

- 経路の形が無い系統（`shapes.json` に無い・まだ焼いていない）
- どちらかの点が線から 60m（`SNAP_MAX_DEG`）以上離れている
- 2点が**別の線**にある（乗り場で折り返す経路などは線が分かれる）
- 2点が**逆向き**に並んでいる

`shapes.txt` は GTFS の任意の項目なので、入っていないデータもありうる。そのときは `shapes.json` を作らず、画面は直線で動く。

### 展示モード（#180）

常盤祭の展示（画面を置きっぱなしにして触ってもらう）用の隠しモードです。

```
/hamakokumap/?kiosk          … 自動でめくる（既定 10 秒ごと）
/hamakokumap/?kiosk=20       … めくる間隔を秒で変える
```

- URL で指定したときだけ。画面からは切り替えません
- 地図を画面いっぱいに出し、見出しは左上、国大／横浜駅の切り替えは右上に重ねます。操作の欄・凡例・一覧は出しません
- 押したときの欄は地図の右上に重ねます
- 出典は右下に小さく残します（ODPT の利用条件で消せない）
- しばらく触られなかったら（`pointerdown` / `keydown` / `wheel` が無かったら）、最初の状態（国大・使うアプリは両方・層は全部・何も選んでいない・全体表示）に戻します
- 台数・バスの自動更新はふつうの画面と同じです

## エリアを増やす

エリアの範囲は #65 で「横国キャンパス＋横浜駅」の2つと決めています。三ッ沢上町・和田町などを足すときは、先に要件を見直してください。手順は次のとおりです（横浜駅はこの手順で足しました）。

1. その周辺のポートの座標から bbox を決める（余白 0.0008 度くらい）。目印になる駅や建物が端に寄らないようにする
2. `areas.json` の `areas` に要素を1つ追加（`id` / `name` / `svg` / `bbox` / `ports`、必要なら `role` と `osm`）
3. 両方の事業者のフィードに載っているポートは、`overrides.json` の `feedIds` で対応づける（同じ場所・同じ名前で ID が違う）
4. `node drawArea.js <id>` で SVG を生成
5. `update.js` を実行
6. 表示を見て `osm.buildingLabels` に目印になる建物を足す。ポートと同じ名前の建物はピンの名前と重なるので載せない

`index.html` は `areas` の数だけタブと地図を作るので、ほかの変更は要りません。タブの名前は `index.html` の `AREA_TAB`（無ければ `name`）です。

### エリアごとの設定（`areas.json`）

| キー | 意味 |
|---|---|
| `role` | `rent`（借りる側。省略時）か `return`（返す側）。`return` のエリアは、地図の札に「返せる空き」を出し、一覧でも返せる空きを大きく出す |
| `departures` | はまこく Exp. の出発地（フォームの `departure` の値）→ その建物の OSM の `name`（#179）。`update.js` が SVG から建物の形を拾い、`ports.json` の `departures` に焼き込む。キーは `app_v1/config/departures.js` の `DEPARTURE_IDS` とそろえていて、ずれるとテストが落ちる |
| `kiosk` | 展示モード（`?kiosk`）だけで使う横長の地図（#180・#181）。`svg` と `bbox` は必須、`osm` を書くと通常の設定に重ねられる。下の「展示モード用の横長の地図」 |
| `ports[].usedByHamakokuex` | はまこく Exp. のルート検索が使うポートなら `true`。地図のピンの番号に輪を付け、一覧に「はまこく Exp. の返却先」と出す。横浜駅の5件は `app_v1/db/transit/cycleport/cycleportlist.json` の `YokohamaStation` とそろえていて、ずれるとテスト（`app_v1/test/hamakokumap.test.js`）が落ちる |
